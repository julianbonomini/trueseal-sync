# Session State is versioned and migrates forward; a Store Reset needs explicit approval

Status: accepted (decided 2026-09-30 in [trueseal-roadmap#20](https://github.com/julianbonomini/trueseal-roadmap/issues/20); not yet implemented). This refines the outbox rule of ADR-0022 and adds one status reason and one error case to ADR-0028. The relay's store follows the same policy in trueseal-relay ADR-0013. Amended by ADR-0034.

The store has no schema version and no migrations today. The preview ADRs already add a lot of durable state: Pending Join, Leaving, Destroying, the dedup table, held manifests and Pending Membership Changes. So 0.6.0 starts a new store format no matter what. This ADR decides what happens between preview releases.

A wipe is costly. Losing Session State also loses the Device identity, so every other member keeps a device that will never answer. For the whole group, a wipe on upgrade amounts to Destroy Group. So upgrades migrate forward by default.

## Decision

- **Store Version.** Session State records the Store Version that wrote it. The first preview release (0.6.0) writes Store Version 1.
- **Migrate by default.** Every TrueSeal Release opens the store of any earlier preview release and migrates it forward. Migrations are chained, and every migration since 0.6.0 stays in the code for the whole preview. A release that skips versions (0.6 → 0.8) still migrates.
- **Store Reset releases.** A release may drop migration and declare itself a **Store Reset** release. That needs the product owner's explicit approval and a release-notes entry. A Store Reset release moves the migration floor to itself.
- **Unmigratable store: automatic reset.** This covers a store from before a Store Reset release, and the unversioned stores left by development builds. The library wipes the namespace, generates a fresh identity, and reports `statusChanged(notJoined, storeReset)`. It follows the same pattern as removal and Destroy Group (ADR-0028). The object stays usable and can pair again.
- **A newer store is refused.** If the store was written by a newer release (a rollback), `open()` fails with the typed error `storeTooNew`. The store is not modified, so rolling forward again loses nothing.
- **Atomic migration.** A migration runs in one database transaction. A crash leaves the old store untouched and the next start retries. A migration that fails outright raises `storage` and leaves the old store intact. The library keeps no pre-migration copy on disk, because a second file holding identity keys would double what is exposed at rest.

## End-to-End Version bumps and the outbox

ADR-0022 says that outbox entries sealed under an old End-to-End Version can't be re-sealed, because the outbox keeps no plaintext. That is true only of app `Sync` bodies. Pair, Group Manifest and Revoke entries are built by the library from Session State. Purging them would stall state machines. A Pending Join whose Pair was purged would wait forever, and a Leaving or Destroying device would wait for relay acceptance that never comes.

- In the migration transaction, the library **rebuilds and re-seals** every Pair, Group Manifest and Revoke entry under the new End-to-End Version. Their Sequence ordering stays unchanged.
- (Superseded by ADR-0034: `Sync` entries are re-sealed too, and nothing is removed.) Only `Sync` entries are removed. Their Message IDs are **persisted** as a pending `UndeliverableAfterUpgrade{messageIds}` Delivery Issue in the same transaction.
- The store opens before any handler exists, so the pending issue is delivered once, when a delivery-issue handler is first registered, and then deleted. Firing it at startup would make the ADR-0026 promise ("you learn about every message the library gave up on") impossible to observe.
- Peers still on the old release keep the re-sealed newer-version Blobs unacked on the Relay (up to the ADR-0022 cap) until they upgrade.

## Crash behaviour

| Crash point | Next start |
|---|---|
| Before the migration transaction commits | Old store intact; migration retries |
| After commit, before the pending Delivery Issue is delivered | Issue still persisted; delivered when a handler registers |
| During an automatic Store Reset wipe | The store is still unmigratable, so the reset runs again |

## Release gate

Every release candidate must pass the following in the E2E suite. Each one is a hard block, like every scenario in trueseal-e2e ADR-0001.

- Open real stores from every earlier release since the migration floor. The fixtures are generated by the released artifacts, not built by hand, and cover these states: member with queued outbox entries, Pending Join, Leaving, Destroying, and a dedup table in use.
- After migration, exchange messages with an un-upgraded peer and with an upgraded one.
- Refuse a store from a newer release, and leave its bytes unchanged.
- Kill the process mid-migration, then recover.
- When a release bumps the End-to-End Version: re-seal the control entries and report the purged `Sync` Message IDs through a handler registered late.

## Considered alternatives

- **Always migrate, with no reset allowed.** Rejected. It would force a migration even for a format change that can't reasonably be migrated during a preview that is openly allowed to break.
- **No promise; any preview release may wipe.** Rejected. Every upgrade would effectively destroy every group, which punishes the developers the preview is for.
- **Migrate from the previous release only.** Rejected. Developers skip releases, and chained migrations are cheap to keep.
- **A typed `StoreIncompatible` error with an explicit reset call.** Rejected. It pushes a recovery flow into every app for a case the library can handle with an existing pattern.
- **Reset on a newer store, or read it on a best-effort basis.** Rejected. A reset destroys identity over what may be a temporary rollback, and best-effort reading risks corrupting the store quietly.
- **Purge every stale outbox entry and end the dependent states.** Rejected. An upgrade would turn a Leave or Destroy Group into a local-only wipe that half finishes without telling anyone.

## Consequences

- ADR-0028 gains the status reason `storeReset` and a 13th error case, `storeTooNew`, in all three SDKs.
- The docs state the upgrade promise. They also say that a Store Reset release ends every group whose devices upgrade to it.
- The Compatibility Table lists each release's Store Version and migration floor.
